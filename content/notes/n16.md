## GiGPO：立下分组的细粒度奖励规矩

![GiGPO 方法示意图](/content/media/gigpo-series-gigpo.png)

GRPO 提供了一种简明有效的强化学习方式：针对同一道训练题采样多条解题轨迹，根据它们在组内的相对表现更新策略。常见做法是“答对得一分、答错得零分”，但二值奖励并不是 GRPO 的限制。

以这种结果奖励为起点，一种改进方向是**丰富反馈**：既区分不同成功轨迹的质量，也为失败轨迹中有价值的步骤提供反馈（给步骤分）。一个直接的想法是让 LLM 评分，但除了提示词设计，还需要解决评分可靠性与奖励作弊等问题。关键不是分数等级越多越好，而是新增的区分能否提供可信、有效的学习信息。

另外一种方式就是**将奖励信号分配到更细的单元上**（如一个 action）。当然，要知道当前哪个 action 的价值最大是相当困难的，这里使用的都是性价比较高的近似算法。

也就是说，**GRPO 使用轨迹级评价，为整条轨迹中的生成 token 提供统一的优势系数；GiGPO 则进一步让不同环境步骤获得不同的优势系数。**

### 方法简介

要进行细粒度的步骤级比较，我认为最重要的一个环节就是比较分组。不过，在这一系列论文中，这个过程被相当简化了（个人感觉这是个雷点）：每个 state 是直接根据训练环境返回的，相当于 agent 在执行下一步时能够得到的信息是什么。可以理解为一个购物智能体：在搜索页是一个 state，在商品页是一个 state。

在分好组之后，组间的比较就直接看这个 action 能往最终拿到奖励的方向推动多少。推动得离成功节点越近，拿到的奖励就越多。例如，动作 a1 发生后还有 3 个步骤成功，动作 a2 发生后还有 6 个步骤成功，那么 a1 拿到的奖励就更多。其实也是一种贪心。

### 为什么重要

相比 trajectory-level attribution，GiGPO 能避免把整条轨迹的终局 reward 机械广播到每一步。它让同 state 的 action 之间形成局部对比，从而更适合多步 agent task。

### 局限

- 只比较“当前 state 一样”的 action，缺少全局任务图视角。
- 如果当前 state 一样但历史 context 不一致，advantage 估计会偏；这正是 [HGPO](#section-5) 处理的问题。
- 无法直接回答某个 action 在整个长程任务中到底有多关键；[G2PO](#section-7) 和 [GraphGPO](#section-6) 更关注这一点。

## HGPO：加入历史的更优分组方式

**我们在一个观测环境下的最佳选择，和我们之前做过的事情高度相关。**

例如，家务机器人的任务是：**“把洗干净的苹果放到餐桌上。”**

当前观察完全一样：

> 你站在厨房，手里拿着苹果，面前是水槽。

但历史不同：

| 历史 context | 此时应该做什么 |
| --- | --- |
| 刚刚已经洗过苹果，然后查看了一下四周 | **去餐桌，放下苹果** |
| 刚从冰箱拿出苹果，还没有洗 | **先洗苹果** |

如果只按当前观察分组，“直接去餐桌”会在一种历史下成功、另一种历史下失败。**评分差异包含了“之前洗没洗过”的影响，不能全归因于当前动作。** HGPO 就通过历史一致性进一步组织比较组。

![HGPO 历史层级分组示意图](/content/media/gigpo-series-hgpo.png)

HGPO 相当于对 GiGPO 中的分组，根据历史的不同进行了进一步细分。这里已经像一个树的结构。这里有个问题是，我们查看代码时，训练环境中的 agent 框架只保留了两步上下文（这里懒得进一步想了）。

HGPO 的漂亮之处在于，它不是简单追求最干净的 oracle group。Oracle group 虽然 bias 低，但样本少、variance 高、利用率差。**HGPO 用层级 group 在两者之间折中。**

## GraphGPO

![GraphGPO 任务图与信用分配示意图](/content/media/gigpo-series-graphgpo.png)

传统 GRPO / trajectory-level group RL 会把最终成功或失败广播到整条轨迹：

- 成功轨迹里的无效步骤也被奖励。
- 失败轨迹里的关键进展步骤也被惩罚。
- 长程 agentic task 的 sparse terminal reward 让这种噪声尤其严重。

GraphGPO 的核心判断是：**agent 的一个 action 是否好，不应该只看它所在 trajectory 最后成功没成功，而应该看它是否让状态更接近任务目标。**

这里的关键思想其实在 GiGPO 中提出了。GraphGPO 的进一步优势是对这个过程进行了合理的图建模，以及对失败轨迹的利用（通过一种向成功轨迹“借距”的方式）。

当然，此处的图建模也让它的缺陷更加明显地体现出来，即这种训练方式会更加推动走最短路径（捷径）。

## G2PO

![G2PO 图结构与价值增益示意图](/content/media/gigpo-series-g2po.png)

我们之前讨论的时候，认为这篇工作在之前系列工作的基础上，创新比较糙，没有太吸引人的点（不过它后面还是中稿了）。

这篇的方法就不细写。整体来说，**我们要以一种高性价比的方式，从轨迹中挖掘有效的信号参与训练**。在图的基础上挖掘是一种很好的方式：一方面可以用算法机械传播，另一方面能有更多数理分析的空间。

## 一些思考

1. **系列工作的组织与延展。** 这一系列工作最成功的原因，在于 GiGPO 构建（基于已有框架调整）得到了一个训练环境。这种感觉就像是在自己布置的赛场上面比赛。GraphGPO 和 HGPO 应该是时期比较接近的工作，但是两个工作解决的是不同点（理论上直接将两个工作缝合起来，会达到更好的效果吧）。它们提供的方式从工程实践上讲都存在许多缺陷，但是都有比较简洁漂亮的方法亮点。G2PO 更像是模仿它们的实验方式、行文逻辑，甚至是绘图配色（是有什么审稿暗语吗，bushi）。当然，这个对于没有入门的人（比如我），感觉是一个相当好的思路。

2. **细粒度的奖励真的更佳吗？** 从方法上看，这些方式很明显会导致走捷径，会导致泛化性差或者安全的问题，要投入实际使用的话还得加噪声。而 GRPO 这类粗奖励的方法，像是天然地带入了一些噪声：也许在特定的测试集上表现会不佳，但是在大数场景中应该会更合适。个人比较看好的是对轨迹划分合适的等级，感觉在工业上这样使用也会比较有效。

3. **一个未继续推进的想法。** 之前想到一种让 agent 先走向信息量最高的 state，再逐渐收敛的训练方式，感觉比较好讲故事，不过后来没资源和精力做下去了。
