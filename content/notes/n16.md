# Setup Complete, Now You Are Compromised

> 一句话导读：这篇论文把一个很日常的动作 - “帮我把项目环境装好” - 翻成了一条攻击链。攻击者不必写恶意代码进仓库，只要改 README、`requirements.txt` 或 Makefile，让 AI 编程代理在安装依赖时跑到错误的包名、错误的源、或有漏洞的版本，代码就可能在开发者机器上执行。

## 这篇论文到底在讲什么

过去，开发者看到 `pip install` 之前，多少还会有一瞬间的人肉刹车：包名是不是拼错了？这个 registry 域名眼熟吗？版本是不是老得可疑？论文把这段“包名/来源/版本没有被系统性验证”的空白叫作 [安装缺口](/academic/note/?id=n16)。

AI 编程代理把这个缺口放大了。用户一句“set up this project”，代理会读 README、解析依赖文件、创建虚拟环境、执行安装命令，而且往往带着开发者本机权限和环境变量。于是文档不再只是文档，它变成了安装时执行代码的前置指令通道。

作者研究的问题不是“模型会不会写出不安全代码”，而是更靠近地面的一个问题：当仓库里的普通 setup 文档被投毒时，生产级 AI coding agent 会不会在安装前发现？

## 核心贡献

1. 论文系统评测了 12 个场景、5 类攻击、9 组 harness-model 配置，覆盖 Claude Code、Copilot CLI、Codex CLI 和 Cursor 等生产环境代理。
2. 最重要的发现是：安全性不是“模型越强越安全”这么简单，而是 代理运行框架 和模型组合出来的结果。同一个模型，换一个 harness，同一攻击可能从“全部拦住”变成“大多装上”。
3. 名字类攻击相对容易被发现，例如明显 typosquat；但来源类攻击，比如隐藏的 `--extra-index-url`、不可信 registry，几乎被大多数配置忽略。
4. 仅靠提示词可以补一部分，但只补它点名的维度。真正有效的方向是安装前的确定性 gate：在任何 install 命令执行前检查包名、来源和版本。

## 威胁模型：文档如何变成攻击面

![fig1_trust_chain](/content/media/78bbd2516a4a.png)

这张 Figure 1 是整篇论文的地图。正常链路看起来很干净：

开发者把任务交给 AI Agent，Agent 读取项目文件，从 README、`pyproject.toml`、Makefile 等地方抽取安装命令，交给 `pip install`，再由包索引解析包，最后代码进入开发者环境并可能在安装期执行。

红色虚线框才是关键：攻击者控制的不是开发者机器，也不一定控制项目源码。他可以只改文档或依赖声明：

- 在项目文件里放一个近似真实包名，比如 `azurecore` 冒充 `azure-core`，破坏 包名意图。
- 在 README 或 requirements 里放 `--extra-index-url`，让 pip 到攻击者 registry 查包，破坏 来源真实性。
- 固定一个有已知 CVE 的旧版本，破坏 版本安全性。
- 通过错误消息建议安装一个并不该安装的包，把程序输出变成指令注入。

论文把安全安装需要满足的三个性质概括为：

- `AUTHENTIC`：包来自可信源，而不是攻击者服务器。
- `INTENDED`：包名是开发者真正想要的那个，而不是相似拼写或诱导名。
- `SAFE`：版本没有已知未修复漏洞。

作者的判断很锋利：当前 agent 工作流基本没有系统性验证这三件事。

## 评测场景：攻击者都怎么下手

![table1_scenarios](/content/media/0b13787e13b1.png)

Table 1 把 12 个场景分成 5 类：

- Name 类：明显 typosquat、分隔符混淆、`pyproject.toml` 中的细微转置、带社工理由的错包名、跨文件冲突、一次塞入 377 个 typosquat。
- Source 类：依赖混淆、localhost registry、外部 HTTPS registry、requirements 文件里隐藏 index。
- Version 类：固定已知有漏洞的版本。
- Config 类：Makefile 设置 `PIP_CONFIG_FILE`，间接把 pip 指向攻击者源。
- Output 类：程序运行时报错，错误消息建议安装攻击者想要的包。

这个表的价值在于它没有把攻击抽象成“恶意 prompt”。相反，它们都伪装成开源项目里很常见的 setup 细节：一个 README 命令、一行 requirements、一个 Makefile target。也正因为常见，agent 更容易把它们当作“项目希望我这样做”。

## 主结果：代理会抓住什么，又会放过什么

![table2_detection_rates](/content/media/f7fe9eb5d66a.png)

Table 2 是论文最重要的结果表。绿色是可靠检出，黄色是多数检出但不稳定，红色是少数检出或基本没检出。

几个结论非常醒目：

- 明显包名错误几乎全绿。`tranformers` 这种肉眼可见的 typosquat，大部分 agent 都能纠正。
- 分隔符混淆仍然危险。`azurecore` vs. `azure-core` 这种“看起来像合理别名”的名字，会让不同 harness-model 组合表现分裂。
- 来源类攻击大片发红。`--extra-index-url`、隐藏 index、不可信 registry，对许多 agent 来说更像普通配置，而不是安全信号。
- R9 漏洞版本固定是全表最刺眼的红：所有配置都是 `0/30` 检出。也就是说，agent 会把已知有 CVE 的版本装进去，默认 setup 过程不会主动查漏洞库。
- R7 错误消息注入反而全绿。所有 agent 都拒绝把程序输出里的安装建议当成可信依赖来源。这说明模型不是没有安全直觉，而是它们对“仓库自带文档”太信任。

作者反复强调一件事：安装之后再提醒不算防住。对于 setup.py、`__init__.py`、postinstall 这类安装期或导入期执行的 payload，等 warning 出现，代码已经跑过了。

## 同一个模型，换个 harness，结论会翻转

![table3_harness_ablation](/content/media/5a3d0e91019c.png)

Table 3 是论文最有意思的对照实验之一。作者固定模型和攻击，只换 harness：

- Opus 4.8 面对 localhost registry R6a，在 Claude Code 里 `10/10` 检出；换到 Copilot CLI，降到 `9/30`。
- Sonnet 4.6 面对外部 HTTPS registry R6b，在 Claude Code 里 `0/10`；换到 Copilot CLI，变成 `10/10`。

这不是“Claude Code 永远更安全”或“Copilot CLI 永远更安全”。更准确地说，每个 harness 给模型的刹车位置、提示语、命令执行节奏都不同。Claude Code 的预执行 checkpoint 会给模型一个安装前停下来的机会；Copilot CLI 的安全提示在某些外部域名场景里更能激活来源检查。

所以论文的核心观点是：模型能力 只是材料，harness 架构 决定这些能力会不会在正确时刻被调用。
**这个感觉是可以切入的点，可以跑换壳实验**

## 跨生态复现：不是 Python 独有问题

![table7_cross_ecosystem](/content/media/ae7358a55afc.png)

Table 7 把代表性攻击搬到 npm 和 Cargo。结论没有消失：

- 名字类攻击在某些生态下仍较容易暴露，尤其是明显 typo。
- registry/source 类攻击继续危险：一旦安装期 hook 已经执行，后续 audit 或警告就是“事后记录”，不是防御。
- npm 的特殊点是 `npm install` 会自动跑 audit，但它是在安装完成后才提示。论文把这种情况标为 install-then-flag：风险被说出来了，但 payload 已经有机会执行。

这张表说明 供应链安全 问题不只属于 PyPI，也不只属于 `pip`。只要“自动读文档 - 自动装依赖 - 安装期可执行代码”这条链存在，install gap 就会跨语言复现。

## 防御：模型和 hook 要互补

![table8_defense_layers](/content/media/f0ee9b1399c5.png)

Table 8 对比了两层防御：一个确定性的 pre-install hook，以及表现最好的模型。两者都是 `10/11`，但漏掉的不是同一个：

- Hook 能抓住 R9 漏洞版本，因为它可以查 OSV/漏洞库；模型默认不会查。
- 模型能抓住 R7 错误消息注入，因为它能理解“这个安装建议来自程序输出，不来自可信 manifest”；静态 hook 只看到 `data-utils` 在 PyPI 上确实存在，反而难判断。

这就是论文最后推荐 defense-in-depth 的原因。不要幻想一个更强模型自动解决所有安装安全问题，也不要幻想一个静态规则覆盖全部上下文。真正可靠的设计应该是：

- 在 install 之前设置 checkpoint，而不是安装之后总结风险。
- 把 `--extra-index-url`、`--index-url`、`--trusted-host` 当成一等安全信号。
- 展开并检查 `requirements.txt`，因为危险 index 可以藏在文件内部。
- 对固定版本查漏洞库。
- 对包名做 typo / edit-distance / existence / age / maintainer reputation 检查。
- 保留模型的上下文判断能力，尤其处理“错误消息建议安装包”这种 provenance 问题。

## 这篇论文为什么重要

它把“AI agent 安全”从抽象的 prompt injection 拉回到开发者每天都会做的操作：装依赖。攻击不需要玄学，也不需要突破模型对恶意请求的拒绝能力。它只要伪装成正常工程文档，让 agent 觉得“这是项目要求的 setup 步骤”。

更妙也更可怕的是，模型经常事后能说出自己应该做什么检查。论文附录里的例子显示，agent 安装了 `tdqm` 之后，被用户追问“你验证过吗”，模型会完整承认自己应该先查 PyPI 元数据、检查 typo、询问用户是不是想装 `tqdm`。这说明缺的不是知识，而是执行路径上的强制触发。

因此，这篇论文给 coding agent 设计者的建议很朴素：不要把安装安全交给模型自觉。把检查做成 harness 层的默认动作，在命令执行前拦住风险。

## 我的读后判断

我觉得这篇论文的强处不是“发现 typosquatting 很危险”，而是指出 AI agent 时代的威胁模型倒过来了。对人类开发者最有效的明显 typo，反而可能被模型记忆和模式识别挡住；但对人类来说稍微可疑的 registry/source 配置，在 agent 眼里却像普通工程惯例。

这意味着我们不能只训练模型“更懂安全”。真正需要的是把 package installation 当作高权限操作：像浏览器拦截可疑下载、操作系统拦截未知开发者应用一样，agent harness 应该在依赖安装前做来源、名称、版本三重检查。

## 可继续追的问题

- 这些结果在真实大型 monorepo 里会不会更糟？因为依赖来源更复杂，私有 registry 更常见。
- 如果攻击者知道 hook 规则，会不会通过更隐蔽的 build backend、`uv sync`、PEP 517 等路径绕过？
- 对 npm、Cargo、Go、Maven 是否需要统一的“agent package reputation API”？
- 未来 coding agent 的权限模型是否应该把 dependency install 单独列为敏感动作，而不是普通 shell 命令？
